## Verification and provenance

The [standalone certificate instructions](../certificates/new_tests_20261011/README.txt)
describe direct execution of all three factors. From the repository root:

```sh
python3 -I -B certificates/new_tests_20261011/verify_all.py
```

The standard-library verifier checks hashes, independently expands the original
source DAGs, compares the uploaded SMS maps, replays every final literal
program exactly, and checks each full matrix multiplication tensor. Final
programs have zero explicit unary negations, nonunit scalar operations or
unused assignments. A/B entries use row-major storage and C uses column-major
storage; this is an ordering convention, not an arithmetic basis conversion.
Source hashes and the exact source checkout are recorded in
[claims.json](../certificates/new_tests_20261011/claims.json).

Original decompositions and historical reductions are credited to
[Andrey Perminov's FastMatrixMultiplication repository](https://github.com/dronperminov/FastMatrixMultiplication).
Completions use his separately installed
[linear-expressions-optimization library](https://github.com/dronperminov/linear-expressions-optimization)
at pinned commit `2abd2fd8f15dc1c97dd24777515324f865e77504`.
This release does not vendor that upstream implementation or its binaries.

## What was combined

Each fixed map received a short portfolio: CSE-only and vector-covering
controls, matched Bernoulli retention 0.5 and 0.9, scored dependency cuts, and
shared-residual forests. The retention controls started from the same exact
incumbent, seed sequence and scorer settings. Scored cuts remove a gate group
and its dependent descendants, preserve the remaining paid program, and ask
the external solver to complete the same outputs. Residual forests create new
exact donor circuits by building shared differences between related targets;
both residual construction and every output reconstruction gate are charged.

All complete exact donors then entered a shared form pool. The pool enumerates
exact alternate binary productions and globally reconnects the required
outputs, allowing useful chains from different circuits to be combined. An
equal-cost or worse donor can contribute valuable intermediate forms. No
timeout or unfinished solver output is admitted as a certificate.

The decoder received a second pooled search in its adjoint orientation.
Searching the original W pool and the WT pool explores different dependency
structures even though linear transposition preserves the underlying map.
Every WT candidate is transposed back with all reverse accumulations paid,
then replayed and oriented with the original W input and output signs fixed.
For example, the 5x5x11 original-W campaign reached 377 additions; the small
WT pool search returned a strict 355-addition original-W program. This is the
same W map, not a free change of the output basis.

The [portable adjoint-pool wrapper](../methods/linear/reconstruction/adjoint_pool.py)
accepts an exact WT donor bank, the original W matrix and an optional current
W candidate. It verifies all maps, preserves coefficient magnitudes, counts
every return gate, and retains the current candidate if the return gives a
longer program. Native exact relation enumeration can reuse a configured
binary or compile locally; the Python relation backend needs no compiler.
This wrapper combines known linear transposition and pooling ideas. The
experiment establishes useful counts on these maps, not general superiority
of the wrapper or a new unrestricted SLP minimization algorithm.

```sh
python3 -I -B methods/linear/reconstruction/test_adjoint_pool.py

# WT_donors.json is a bank of complete programs for transpose(W.sms).
python3 -I -B methods/linear/reconstruction/adjoint_pool.py \
  --donors methods/linear/reconstruction/adjoint_pilot/5x5x11/donors.json \
  --matrix certificates/new_tests_20261011/5x5x11/W.sms \
  --candidate certificates/new_tests_20261011/5x5x11/W.json \
  --out /tmp/fmm-adjoint-pool --search-seconds 20 --seed 11117000
```

The default exported numeric candidate uses the signed-wire search model.
Add `--orient-seconds 8` to request optional OR-Tools fixed-sign feasibility
and a literal `best.slp`. This differs from the existing joint U/V/W
orientation CLI, which allows compensated product signs. Here every original
input and ordered output sign is frozen. An infeasible or timed-out sign pass
does not certify a strict count. `--backend python --search-seconds 0` tests
pool composition and paid return using only the standard library; plateau
search itself requires a C++17 compiler. Output directories cannot be reused.

## Controls and timing

Across the eighteen fixed maps, retention 0.5 had a lower completed-or-inherited
signed count on three maps, retention 0.9 on ten, and five tied. These small
time-limited controls used the same incumbent and seed sequence per map.
They compare heuristic outcomes, not optima, and inherited unchanged
incumbents are distinguished from actual completed repairs in the
[retention records](../certificates/new_tests_20261011/matched_retention_controls.json).
The upstream sampler also discards descendants whose parents were removed,
so a 0.5 gate-retention parameter does not retain half of every usable chain.
Both retention settings remain useful sources of donor diversity.

A separate frozen-bank guided-initialization control on 5x5x11 U used twelve
starts: random versus marginal-gain chain selection, gate budgets 40 and 80,
three starts per condition. At budget 80, the guided arm completed all three
calls and attained a signed 204, while the random arm completed one and
attained 211. Both budget-40 arms timed out. This did not improve the already
strict-certified U195 program and does not demonstrate a contribution to the
final bound. Guided initialization remains a pilot lead rather than the
explanation for these certified counts.

The base portfolio used one upstream thread per map, eight-second wall
budgets per donor method, two-second per-call repair limits, and a 25-second
pooled search. Three independent map processes ran concurrently. The extra
WT searches used existing donors and twenty-second search budgets; they did
not regenerate donors. Donor assembly, native relation construction, search
subprocess time, strict orientation and total wall time were recorded
separately. Reused toolchain build time is not silently described as search
time. Cold eight-second CSE/vector-cover timeouts are incomplete runs and do
not show that those methods cannot improve the maps.

For the 5x5x11 WT follow-up, existing-donor preparation took 0.450 seconds,
pool assembly 0.160 seconds, the twenty-second search subprocess 21.157
seconds, and strict orientation 0.550 seconds; total wall time was 22.703
seconds. The corresponding 5x6x8 follow-up took 22.366 seconds in total.
These are search pipeline measurements on the local machine, not matrix
multiplication execution timings or portable speed guarantees.
